## Compatibility policy

github-sts follows [Semantic Versioning](https://semver.org). While the project is pre-1.0:

- **Minor (`0.X.0`)**: new features and may contain breaking changes; read release notes before upgrading.
- **Patch (`0.0.X`)**: bug fixes and non-breaking improvements.

Breaking changes are called out at the top of each release's notes on GitHub.

| Component | Compatibility |
|---|---|
| Go client (`client/`) | Same major/minor as the server; minor version bumps may add new methods but won't remove existing ones pre-1.0. |
| Trust policy schema | Backwards-compatible additions only. New required fields (e.g. `audience`) are introduced behind a deprecation window: see release notes. |
| Configuration (YAML / env) | Backwards-compatible additions only. Removed/renamed fields emit a startup warning for one minor version before removal. |
| HTTP API (`/sts/exchange`) | Stable request/response shape. New optional parameters and error `code`s may be added; existing ones won't change meaning. |

## Release process

1. Release notes are auto-generated by [release-please](https://github.com/googleapis/release-please) from Conventional Commits.
2. Breaking changes are called out manually in the release description.
3. Docker images are built and signed with cosign keyless signing.
4. The Helm chart is updated in a coordinated release.

See [Releases](https://github.com/Depthmark/github-sts/releases) for the full history.

## Migration: `audience` field

The `audience` field is mandatory in every trust policy. A policy without it is rejected at parse time.

**Before:**

```yaml
issuer: https://token.actions.githubusercontent.com
subject: repo:org/repo:ref:refs/heads/main
permissions:
  contents: read
```

**After:**

```yaml
issuer: https://token.actions.githubusercontent.com
subject: repo:org/repo:ref:refs/heads/main
audience: https://sts.example.com
permissions:
  contents: read
```

**Step-by-step migration:**

1. Choose an audience value unique to your STS deployment (e.g., `https://sts.example.com`).
2. Add `audience:` to every trust policy.
3. Update every workflow's `core.getIDToken()` call to use the chosen audience.
4. (Optional) Set `GITHUBSTS_OIDC_REQUIRED_AUDIENCE` as defense-in-depth.
5. Deploy the updated github-sts version.
6. Verify exchanges succeed; check `audience_mismatch` errors in metrics and logs.

## `immutable_subject` is not a supported field

The `immutable_subject` field is not part of the current policy schema. Unknown keys are ignored by the YAML parser, so a policy containing `immutable_subject` is accepted but the field has no effect. Use `subject` for an exact match or `subject_pattern` for a regex.

**Before:**

```yaml
issuer: https://token.actions.githubusercontent.com
immutable_subject: repo:myorg/myrepo:ref:refs/heads/main
permissions:
  contents: read
```

**After:**

```yaml
issuer: https://token.actions.githubusercontent.com
subject: repo:myorg/myrepo:ref:refs/heads/main
audience: https://sts.example.com
permissions:
  contents: read
```

## Migration: immutable GitHub identity

GitHub.com trust policies require `github.sources[]` and `github.target` (exact immutable `owner_id`/`repository_id` pairs) in addition to a workload selector (`subject`, `subject_pattern`, or `claim_pattern`). See [Trust Policies]({{< relref "/concepts/trust-policies" >}}) for the schema and examples.

For a repository still using GitHub's legacy subject format, coordinate these steps to avoid locking out its workflow:

1. Record the immutable owner and repository IDs.
2. Opt the repository in to immutable subject claims in GitHub.
3. Confirm a newly minted token contains the expected IDs in `sub`, `repository_owner_id`, and `repository_id`.
4. Update its target trust policies to add `github.sources[]`/`github.target`.
5. Deploy the default-on broker configuration (`oidc.require_immutable_subject_claims: true`).

The checked-in `Depthmark/github-sts` release policy expects owner ID `268749784` and repository ID `1198676434`. Opt that repository in before merging the policy migration. The legacy server opt-out (`GITHUBSTS_OIDC_REQUIRE_IMMUTABLE_SUBJECT_CLAIMS=false`) does not make an exact immutable trust policy match a legacy token.

## Pre-upgrade checklist

1. Read the release notes for breaking changes.
2. Check the [Compatibility]({{< relref "/integrations/compatibility" >}}) matrix for verified component combinations.
3. Test in a staging environment.
4. Update trust policies if schema changes are required.
5. Deploy with a canary or blue-green strategy.
6. Monitor `githubsts_oidc_validation_errors_total` and `githubsts_token_exchanges_total` for regressions.
